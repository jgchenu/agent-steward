# 接入真实项目并交付草稿 PR

每次派活明确选择“只读分析”或“允许修改”。默认只读；修改能力还需要本机项目配置许可。任务创建后不能通过继续对话提升模式，请重新派一个修改任务。

## 配置一个 Git 项目

保留现有 `sandbox`，在私人 `steward.config.json` 的 `projects` 中加入自己的项目。下面以 Node 项目为例；命令必须对应项目实际使用的验证方式。

```json
{
  "myproject": {
    "path": "/absolute/path/to/myproject",
    "sandbox": "workspace-write",
    "worktree": {
      "baseRef": "origin/main",
      "checks": [
        { "name": "安装依赖", "command": "npm", "args": ["ci", "--ignore-scripts"], "timeoutSeconds": 300 },
        { "name": "项目验证", "command": "npm", "args": ["run", "check"], "timeoutSeconds": 300 }
      ],
      "github": { "repository": "YOUR_ACCOUNT/YOUR_REPO", "baseBranch": "main" }
    }
  }
}
```

项目路径必须是已有 Git 仓库的根目录。`baseRef` 使用 `origin/main` 时，每次新任务会先 fetch 对应远端分支。未提交改动不会带入任务。没有远端的本地试验可使用 `main` 并省略 `github`，但无法通过卡片创建 PR。只读项目也可以配置 worktree 来获得独立目录。

准备 PR 需要本机 Git 提交身份，以及自行完成 `gh auth login`。当前只支持标准 GitHub.com HTTPS/SSH origin URL，并要求 URL 与配置的仓库一致。不要把凭证写进 URL。

`checks` 是部署者配置的可信本地程序，逐条执行，不经过 shell 拼接。验证进程不继承飞书密钥、API Key 等服务环境变量，但仍作为本机用户运行，能够使用其文件和网络权限；worktree 只隔离 Git 工作文件，不是操作系统沙箱。只接入信任的仓库和检查命令。

新目录不复制主目录的 `.env`、`node_modules` 或未跟踪文件。需要安装依赖时配置适当的检查命令；`--ignore-scripts` 是否适合项目由部署者决定。不要复制生产密钥作为修复手段。旧版本仅设置 `workspace-write` 的配置需增加 `worktree` 才能启动。

## 从飞书完成任务

1. 在群里 @分身，说明项目、要改什么和验收标准；也可使用工作台选择项目和模式。
2. Steward 建立 `.steward/worktrees/<任务ID>` 和 `steward/<任务ID>` 分支，Codex 在其中工作。需要扩展权限时仍通过独立请求确认。
3. Codex 返回后，Steward 自行统计真实文件改动，执行配置中的检查，记录退出码和本机日志。
4. 打开“查看交付”，核对文件列表和各项检查状态。工作目录和日志保留在本机，可以用编辑器查看完整 diff。
5. 验证全部通过且存在改动时，在原话题 @分身说“创建 PR”，或从详情点击“预览 PR 交付”。卡片展示目标仓库、分支、标题和完整 PR 正文；确认后程序才提交和推送任务分支、创建草稿 PR。已有开放 PR 会复用。
6. 使用“打开 PR”在 GitHub 审查。审查后可明确确认让分身代为合并；部署结果需单独验证。“确认完成”只记录任务验收，不会发布。

验证失败、没有配置检查、验证命令修改了交付文件，或验证后又改动了文件，都会阻止 PR 交付。继续任务会使上一次验证失效。检查配置变化也必须重新验证。

如果远端目标分支已经前进，交付会停止，保留工作目录；当前需要基于最新版本新建任务并明确迁移所需改动，不自动 merge/rebase/reset。如果任务分支的 PR 已关闭或合并，也需要新建任务。取消和失败保留已有修改；不自动删除 worktree 或分支。

终端 `/new <项目> <要求>` 是只读，`/edit <项目> <要求>` 请求修改。飞书 `/publish <任务ID>` 仅打开预览，真正发布需要点击确认；终端暂不提供发布确认入口。

## 验证范围

`npm run check` 使用真实临时 Git 仓库、独立验证子进程和模拟 GitHub 响应，无外部账号依赖。`npm run smoke:workspace` 单独消耗少量 ChatGPT 订阅额度，在临时仓库做一次真实修改并检查原目录未变化；不会创建远端 PR，也不批准扩展权限。

模型声称运行过测试，不会替代程序记录的检查。配置检查通过、GitHub CI 通过、浏览器验收、人工接受、合并和部署分别判断。创建 PR 的发布器不会顺带合并；合并有独立的一次确认流程。传给 Codex 的“不自行提交发布”等指令不构成外部工具权限防火墙，仍需配合仓库保护。

## 更换任务代码版本

发现截图/线上实现与任务代码不一致时，在原话题 @分身或引用回复它说“更新代码版本”；也可从任务详情点击“更换代码版本”，或发送 `/baseline <任务ID>`。填写明确的 Git 分支或提交 SHA，例如 `origin/main`。这不是把远端 main 合入旧功能分支。

Steward 会先解析版本（`origin/` 分支先 fetch），展示当前版本、目标完整 SHA、旧副本改动数量。点击“允许本次”后，创建新任务、新 Codex 会话和独立分支，保留原需求与最近补充，并把话题接到新任务。新任务固定到刚确认的 SHA；分支随后前进也不会偷偷改变这次代码。旧任务、工作区、未提交文件及原会话全部保留，**不自动迁移改动**，项目默认 `baseRef` 也不改变。

拒绝不会建立新副本。等待期间旧工作区或项目授权发生变化则停止，要求重新预览。取消/重启后旧确认失效。执行中的任务须先停止；普通“可以”不会确认更换版本。终端 `/restart <任务ID> <ref>` 也只准备预览，仍需明确 `/approve`。选定版本与配置的 PR 目标不一致时不能发布；仍必须遵守项目对分支和生产发布的限制。

## 浏览器确认

Codex 的 `mcpServer/elicitation/request` 表单确认会转到飞书：展示工具来源和请求内容，空字段确认使用“允许本次 / 拒绝”，不会附带持久化或整个会话的授权。结构化的简单字段使用显式 JSON 回答，普通话题聊天不会回答工具权限表单。支持字符串、布尔、数字、整数及有限的枚举/长度/数值约束；复杂字段、敏感输入、认证 URL 流程和身份验证不通过群聊处理，会明确取消而非自动接受。

协议以本机 Codex 生成的类型及 [官方 App Server 文档](https://learn.chatgpt.com/docs/app-server#MCP-server-elicitation-requests)为依据。确认仍绑定主人、原会话、当前请求；重复点击、服务端撤销、取消和进程重启不能重放。真实的浏览器权限拒绝不能通过别的浏览器、CDP 或网络请求绕开。

依赖登录态的验收只使用已连接 Chrome 扩展和已有目标标签页。Chrome 不可用、目标页缺失或登录失效时报告阻塞；不会退回内置浏览器或读取登录凭据。工具确认接通不等于页面验收通过：仍需实际检查页面并记录证据。

## 看清实际代码来源

独立 Git 副本准备并核验后，会先在话题回复一条简短回执：项目、基准分支/引用、基准 SHA、开始时提交，以及副本已有改动数量。这条回执来自 Git 检查，不依赖模型自述；准备失败不会声称已使用某个版本。

主卡片只保留结果、简短代码来源和“查看详情”（执行中另有“停止”，已有 PR 时提供 PR 链接）。详情中的“代码与验证记录”可展开查看完整来源；在原话题 @分身或引用回复它说“代码来源”“查看代码来源”“当前代码版本”，或发送 `/source <任务ID>` 也可以。查看不启动模型、不回答待审批请求、不切换分支。

详情显示完整基准 SHA、任务分支、最近检查提交、相对基准累计改动文件数和检查时间。群聊隐藏本机绝对路径；私聊可看来源和执行目录。运行时显示最近一次记录，**不代表实时 HEAD、远端最新版或线上部署版本**。未准备工作副本时，配置来源明确标为“尚非执行证据”；未配置 Git 副本的只读目录不虚构提交 SHA。

## 减少执行过程中的手动审批

在运行分身的电脑上打开 http://127.0.0.1:17831/，选择审批方式，保存后约一秒内热更新。页面分别显示已保存模式、机器人已应用模式及当前执行模式：

- **请求批准**：`permissionMode: "ask"`，沙箱内已允许的操作直接执行，触及边界时向主人请求一次批准，并非每条读取都询问。
- **关键审批**：`permissionMode: "auto"`，使用 Codex 官方自动审查；仍需人工决定的请求转到飞书。自动审查可能拒绝操作，不代表所有危险动作都会先询问。
- **沙箱内直接执行**：`permissionMode: "sandbox-auto"`，修改任务保留工作副本写入限制、允许联网，使用分类执行审批（执行提权拒绝、MCP 确认仍可送达）；越界拒绝，不自动扩大权限。只读任务仍只读且不开放网络。这是写入沙箱，不是隔离所有本机读取和外部工具的虚拟机。
- **完全访问权限（高级）**：`permissionMode: "full-access"`，修改任务使用无沙箱文件/网络访问及分类执行审批策略（MCP 确认仍可送达）。首次切换需在保存前明确勾选访问范围；项目列表不再构成系统级隔离。只读任务仍使用只读沙箱，不自动允许联网或提升为修改。

放宽权限从下一轮执行（含继续任务）生效；当前任务保持启动时的模式，已弹出的请求不会被追溯批准。收紧权限会停止仍使用更宽权限的任务，已有改动保留，再次继续使用新模式。浏览器应用层确认、Steward 更换基准与草稿 PR 发布确认保留，禁止自动合并/部署的规则保持有效。

旧配置只有 `approvalsReviewer` 时兼容映射为请求批准或关键审批，不会自动启用完全访问。显式 `permissionMode` 优先。机器人离线时页面只报告已保存，等待启动支持该配置的新版服务。账号、客户端及组织策略可能限制模式；被拒绝时不绕过、不自动降级到全权限。参见 [OpenAI 权限模式](https://learn.chatgpt.com/docs/permission-modes)与[自动审查](https://learn.chatgpt.com/docs/sandboxing/auto-review)。


## 截图交付

修改任务会获得本轮专用 `.steward-delivery/run-*/` 产物目录。需要 UI 验收时，执行 Agent 使用实际浏览器截图，并将图片和 `images.json` 放在该目录：

```json
[{"file":"desktop.jpg","caption":"桌面 · 模拟数据 · 点击柱子显示平台数量和占比","scope":"local-preview"}]
```

目前支持至多 3 张 PNG/JPEG/WebP，每张最多 5 MiB，说明最多 300 字；`scope` 为 `local-preview` 或 `deployed`。只接收简单文件名，不接受 URL、子目录、软链接或硬链接。不提供 manifest 时不发送图片；非法产物会明确提示检查失败。失败或取消的执行不自动收集图片。

飞书机器人需开通应用身份权限 `im:resource:upload`（或已有的 `im:resource`），并完成所需应用发布；发文字权限不包含图片上传。权限不足时图片保留在 outbox 等待重试，不要求用户重新派活。

Steward 校验后将图片快照和哈希保存在本机私有状态目录，通过持久化 outbox 上传并以飞书原生图片回复到原话题。重试使用固定消息 UUID，已确认发送的图片不重复发送。图片说明明确区分本地预览与已部署页面；截图由执行 Agent 提供，不代替独立验收或发布证明。截图目录不计入代码改动，也不会被 PR 发布器提交；仓库已跟踪该保留目录时会停止任务。私有快照目前随状态目录保留，没有自动清理策略。

“创建 PR”只打开现有交付预览，不直接启动模型或隐式发布。缺少 GitHub 目标、检查配置、验证结果或基准不一致时，预览给出具体原因。确认后的提交、推送和草稿 PR 行为沿用原有保护。

在已有修改任务话题里，也可以自然地说“可以的，提交代码创建 PR 到 main”“帮我把这些改动提个合并请求”或“修好后提 PR”。执行 Agent 理解本轮要求和会话上下文，完成需要的改动后，把结构化发布意图交给 Steward；Steward 运行独立检查并发送发布预览或具体阻塞原因，无需再重复固定口令。明确指定的仓库或目标分支与项目配置不一致时会停止交付，不能静默换成配置中的目标。模型提议本身不会提交、推送或合并，仍由现有预览卡片确认具体交付；单独的“可以”、讨论原因或引用他人消息不会成为发布授权。


## 确认后代为合并

`staging` 继续遵守人工审查、手动合并规则，不进入代为合并流程。

在该项目的话题里 @分身说“合并 PR https://github.com/组织/仓库/pull/123”。已有正式交付 PR 记录时，可以只说“帮我合并”。终端或私聊可用 `/merge <任务ID> <PR链接>`。

分身先查 GitHub，展示 PR、来源与目标提交、检查结果和改动范围，再请求一次明确确认。确认范围包括 squash 合并，以及必要的草稿转待审阅；不会自动等待检查后合并。尚无检查、检查失败/未完成、冲突、需审查或版本变化时停止。项目须已授权修改，PR 必须属于该项目 origin；配置了交付目标时还须匹配目标。跨仓库 PR 暂不支持。

普通“可以”不会回答合并审批；使用当次确认按钮。取消、进程重启或旧卡片不能复用授权。只处理 GitHub 上展示的提交，不推送本地未提交代码；不删除分支，不启用 auto-merge，不强制绕过保护。合并可能触发仓库已有 CI/CD，不代表部署验证完成。发布后应继续在新任务处理新改动。
